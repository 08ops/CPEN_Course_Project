1. Introduction

1.1 What the brief asks for

The requirement, verbatim

"Develop an API/web service that implements the functions you created in Project 1." Submission must include the source code of the API/web service, all scripts used to create the database, a backup of the database, and a report.

Project 1 produced a PostgreSQL database, cpen208_ceds, holding the Computer Engineering Department's student records, fees, course registrations and teaching assignments — together with 19 callable stored functions, the most important of which returns every student's outstanding fees as a JSON array. Project 2 puts that database on the network.

1.2 What "implements the functions" was taken to mean

There are two readings of the brief. The weak reading is: build an API that does the same things the Project 1 functions do — re-deriving the outstanding balance in JavaScript, re-checking class capacity in JavaScript, and so on. The strong reading is: build an API that calls those functions, so that the rules exist in exactly one place.

This project takes the strong reading, deliberately. Under the weak reading the system would contain two independent definitions of "outstanding fees" — one in SQL and one in TypeScript — and they would eventually disagree. The bug would surface as the dashboard and the API quoting different balances for the same student, and it would be nobody's obvious responsibility to fix. Under the strong reading that class of bug cannot occur.

The design rule this project follows

The API performs no business arithmetic of its own. Its responsibilities are transport, authentication, authorisation, input validation and error translation. Every figure it returns and every rule it enforces comes from a Project 1 stored function.

2.1 Where the logic lives

2.2 Request lifecycle

A request for the outstanding-fees report passes through seven stages:

  1. Edge middleware — helmet sets security headers, CORS is checked against the allow-list, the rate limiter counts the request, and the body size is capped at 100 kB.
  2. Authentication — requireAuth extracts the Bearer token and verifies its signature, issuer, audience and expiry.
  3. Authorisation — requireRole('admin', 'lecturer') rejects students with 403.
  4. Validation — the zod schema parses and coerces the query string, so ?indebtedOnly=true becomes a real boolean.
  5. Service — getOutstandingFees() issues one parameterised call: SELECT finance.fn_outstanding_fees_json($1,$2,$3).
  6. Response — the JSON array is wrapped in the standard envelope with a count and the name of the source function.
  7. Errors — anything thrown along the way reaches one error handler, which maps it to a status code and a machine-readable code.

3. API Design

3.1 Conventions

The base path is /api/v1, versioned from the first commit so a future v2 can run alongside without breaking existing clients. Every successful response shares one envelope, and every failure shares another, so a client never has to guess at the shape: 

// success
{ "success": true,
  "data": [ ... ],
  "meta": { "count": 36, "source": "finance.fn_outstanding_fees_json()",
            "timestamp": "2026-08-03T20:18:09.793Z" } }

// failure
{ "success": false,
  "error": { "code": "CHECK_VIOLATION",
             "message": "Assignment would put TA 3 at 40 hours/week, above the contracted maximum of 12" },
  "meta": { "path": "/api/v1/teaching/ta-assignments", "method": "POST",

GET /api/v1 returns a self-describing index of every endpoint at runtime, so the service documents itself rather than relying on documentation that can go stale.

4. The Required Function over HTTP

The headline endpoint returns, unmodified, the JSON array produced by the Project 1 function. The entire service-layer implementation is four lines: 

export function getOutstandingFees(filters: {
  academicYearId?: number; programmeId?: number; indebtedOnly?: boolean;
}) {
  return callJson('finance.fn_outstanding_fees_json($1, $2, $3)', [
    filters.academicYearId ?? null,
    filters.programmeId ?? null,
    filters.indebtedOnly ?? false,
  ]);
}

There is no reduce, no subtraction and no rounding in TypeScript. The three optional query parameters map one-to-one onto the function's three optional arguments, so the HTTP surface offers exactly the flexibility the function already had, and nothing more.

5. Authentication and Authorisation

5.1 JWT issuance

POST /api/v1/auth/login accepts a username, index number or e-mail with a password. The service loads the account, compares the supplied password against the stored bcrypt hash, and on success signs a JWT containing the user id, username, role, and — importantly — the resolved studentId and lecturerId.

Carrying those two ids in the token is what makes per-record authorisation cheap: deciding whether a caller may read /students/42 is then a comparison against the token, not an extra database round trip on every request.

An unknown username and a wrong password produce the identical response. The unknown-user branch even performs a dummy bcrypt comparison, so the two paths take comparable time and the endpoint cannot be used to discover which accounts exist. This is asserted by a test that compares the two error messages directly.

6. Validation and Error Handling

6.1 Request validation

Every body, query string and path parameter is parsed by a zod schema before a handler runs. The schemas are strict: an unrecognised key is rejected rather than silently ignored, so a client that misspells a field learns about it immediately instead of wondering why the value had no effect. Validation also coerces, which matters because everything in a URL is a string — ?indebtedOnly=true reaches the handler as a boolean and /students/42 as a number. 

POST /api/v1/fees/payments
{ "studentId": 1, "billId": 1, "amount": -100, "method": "bitcoin" }

→ HTTP 400
{ "success": false,
  "error": {
    "code": "BAD_REQUEST",
    "message": "Invalid request body.",
    "details": [
      { "field": "amount", "message": "Too small: expected number to be >0" },
      { "field": "method",
        "message": "Invalid option: expected one of \"bank_transfer\"|\"mobile_money\"|…" }
    ] } }

Note that both problems are reported at once. Returning only the first error would force a client into a guess-and-retry loop.

6.2 Translating SQLSTATE to HTTP

Because the rules live in the database, the API must turn a database rejection into a sensible HTTP answer. The Project 1 functions raise errors with meaningful SQLSTATE codes, and src/errors.ts maps them:

SQLSTATEMeaningHTTPExample
P0002no_data_found404Unknown student id
23505unique_violation409Duplicate registration; second lead lecturer
23503foreign key violation409Reference to a non-existent offering
23514check_violation422TA over their contracted weekly hours
22P02invalid input syntax400A non-numeric id reaching the database
08006, 57P01connection failure503Database restarting

Anything unmapped becomes a 500 with a generic message — the raw driver error is logged server-side but never returned, so internal structure is not leaked to a caller. Stack traces appear in responses only when NODE_ENV is not production.

The payoff

"A teaching assistant may not exceed their contracted weekly hours" is written once, in academics.fn_assign_ta_to_lecturer. It is enforced identically for psql, for the Next.js dashboard, and for an HTTP client — and through HTTP it arrives as a correct 422 Unprocessable Entity carrying the database's own explanatory message. Nothing about that rule is written in TypeScript.

7. Security Measures

ControlImplementation
SQL injectionEvery value is a bound parameter ($1, $2, …). No user input is ever concatenated into SQL.
Password storagebcrypt, cost 10. Plain passwords are never stored, logged, or returned.
Account enumerationUnknown user and wrong password return identical responses; a dummy hash comparison equalises timing.
Brute forceGlobal limit 300 requests / 15 min; 20 on /auth/*. Failed attempts are counted on the account.
Transport headershelmet with a strict Content-Security-Policy; x-powered-by disabled.
CORSExplicit allow-list from CORS_ORIGINS; the wildcard is a development default only.
Payload sizeBodies capped at 100 kB — nothing this API accepts is large.
Token integrityIssuer and audience are verified alongside the signature, so a token minted for another service is rejected.
Secret managementJWT_SECRET is mandatory in production — the service refuses to start without it. .env is git-ignored.
Least privilegeGuards on every non-public route; students are confined to their own rows.

Information leakageUnmapped database errors return a generic message; stack traces are suppressed in production.

8. Testing

8.1 Strategy

The suite contains integration tests, not mocked unit tests. That is a deliberate choice: the entire claim of this project is that the API faithfully exposes the Project 1 database functions. A mock of the database would be a mock of the very thing under test, and would pass happily while the real SQL was broken. The tests therefore boot the real Express application against the real cpen208_ceds database.

The app is exported from src/app.ts separately from src/index.ts, which owns listen(). This lets the suite start the service on an ephemeral port in-process rather than spawning a second one. The suite is read-mostly; the single write it performs — registering a throwaway account — is removed in the teardown hook.

8.3 Tests that matter most

Any suite can assert that a 200 is a 200. These are the cases that would actually catch a regression:

TestWhat it protects against
Re-derives outstanding = billed − paid for every row of the reportA silent arithmetic regression in the SQL — the single most consequential figure in the system
Asserts no student's balance is ever negativeThe exact double-payment bug found during Project 1 development
Asserts the fee statement and the balance endpoint agreeTwo functions drifting apart
Confirms pending/reversed payments are excluded, by querying the fixture firstThe central fees rule; the test fails loudly if the fixture ever stops containing an unconfirmed payment
seats_left = capacity − enrolled for every offeringAn inconsistent view definition
Duplicate registration returns 409The unique constraint no longer reaching the client correctly
A second lead lecturer returns 409The partial unique index being dropped
Over-committing a TA returns 422The hour cap in the stored function being bypassed
A student reading another student's record returns 403A broken row-level guard — a genuine data-protection failure
Unknown user and wrong password return identical messagesAccount enumeration creeping back in
An unknown key in the body returns 400Schemas quietly becoming permissive

Several of these assert on the database's behaviour reaching the client intact. That is the point: they would fail if someone "helpfully" reimplemented a rule in TypeScript and let the two definitions diverge.

The service performs a database pre-flight check at startup and exits with a clear message if PostgreSQL is unreachable. A service that starts "successfully" and then returns 500 on every request is worse than one that refuses to start.

12. Limitations and Future Work

Limitations

  • Tokens are stateless and therefore not individually revocable before expiry; the two-hour lifetime bounds the exposure. The browser application uses revocable server-side sessions instead.
  • Rate limiting is in-process, so it resets on restart and is not shared across instances. A multi-instance deployment would need a Redis-backed store.
  • The endpoint index is hand-maintained rather than generated; a machine-readable OpenAPI document would be better.
  • List endpoints return complete result sets. At the current scale (36 students) that is correct; at thousands it would need cursor pagination.
  • There is no refresh-token flow, so a client must re-authenticate every two hours.

Future work

  • Generate an OpenAPI 3.1 document from the existing zod schemas, and serve Swagger UI from it — the schemas already contain everything required.
  • Add refresh tokens with rotation and reuse detection.
  • Move rate limiting to a shared store so the service can scale horizontally.
  • Add structured request logging with correlation ids to tie an HTTP request to its app.audit_log rows.
  • Enable PostgreSQL row-level security so the database enforces the "students see only their own rows" rule even if an API guard were ever removed.

13. Conclusion

The brief for Project 2 asked for an API that implements the functions created in Project 1. That has been delivered as a versioned REST service exposing 24 endpoints across all five required functionalities, with JWT authentication, a role- and row-level authorisation model, strict input validation, a coherent error contract, and 43 passing integration tests.

The defining decision was to treat "implements" as calls rather than reimplements. Every figure the service returns and every rule it enforces comes from a PostgreSQL stored function written in Project 1. The clearest demonstration is the 422 in §9: rejecting an over-committed teaching assistant required no TypeScript at all, because the rule was already in the database and the API's only job was to carry the refusal back to the caller with the right status code.

The result is that the Next.js application from Project 1 and this REST service are two faces of one system rather than two systems that happen to share a database. Neither can quote a different outstanding balance from the other, because neither computes one.
